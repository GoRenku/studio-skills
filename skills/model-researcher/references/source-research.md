# Research useful model guidance

## Find prompting sources, not just endpoints

Resolve the exact model, version, tier, provider, and requested operation first.
Keep route identity and creative advice separate: an API reference can establish
accepted fields and limits without explaining how to obtain a good result.

For normal additions and guidance refreshes, search for the model's prompt guide,
user guide, worked examples, and relevant operation advice. Check the model
developer's documentation, blog, official repository or model card, and the
selected provider's learn/blog material. Follow substantive guide links from
those pages. Do not conclude that prompting material is absent after reading
only a route page or its schema.

Prefer sources in this order, according to what they actually explain:

- Model-developer prompting guides and examples for the exact version.
- Substantive provider tutorials with explained prompts or demonstrated results.
  A developer-authored article hosted by a provider can be a primary source.
- Official technical docs and model cards for capabilities, syntax, and limits;
  retain prompt advice when the page genuinely includes it.
- Clearly identified secondary material only when primary guidance leaves a
  relevant gap. Distinguish the author's observations from developer guarantees.

Verify the publisher. A model-branded domain or an article calling itself
"official" does not establish affiliation. Marketing claims, copied summaries,
and lists of API fields do not establish tested prompt-quality practices.

Check version and surface boundaries. A developer's application may support an
editing mode that the selected provider route does not expose. A newer speech
model's tags or music model's composition controls are not facts about an older
route. Use shared-family advice where justified, and qualify or omit unsupported
variant-specific conclusions. Do not change the selected model to fit a source.

When sources disagree, compare the version, operation, provider surface, and
publication or update context. Prefer current primary guidance for its actual
scope, and explain a consequential disagreement rather than presenting either
source's rule as universal.

## Turn research into useful advice

Read existing guidance before refreshing it. Preserve useful examples, accepted
workflow rules, deliberate preferences, and unrelated edits. Source quality,
not file age or length, decides what needs improvement.

Retain the advice that materially helps someone prepare this model's request:

- A concrete prompt construction pattern, including when compact prose or more
  structured direction is useful. Attribute length or syntax recommendations;
  do not invent universal word counts or mandatory headings.
- Guidance for the important requested modes: motion versus appearance, frame
  anchoring, reference roles, edit scope, typography, or speech/music direction
  as relevant. Cover meaningful differences rather than repeating one generic
  subject/light/camera recipe for every operation.
- Original, adaptable examples with a short explanation of the decisions they
  demonstrate. Label authored examples as untested unless they were actually
  executed; a provider's demonstrated example does not test our new prompt.
- Relevant failure symptoms and a focused rewrite or input-selection change.
  Attribute observed failures; label an inferred cause or repair as an agent
  recommendation rather than a proven model defect.

Separate documented behavior, provider-author observations, and agent
recommendations in the prose. Link the sources that support consequential advice
near that advice, and record when they were read. A route-check date is not a
prompting-research date. Do not use "recovered from earlier research" as the only
provenance, copy vendor prompts wholesale, or infer comparative quality from
marketing, matching schemas, tier names, or latency.

Keep guidance proportional to the evidence and task. No prescribed headings,
research dossier, source-count quota, or completeness score is needed. Shared
workflow rules may be linked rather than duplicated. Creative guidance belongs
to the agent/user loop; never turn these editorial checks into runtime prompt
validation, capability matrices, or model-availability requirements.

## Review the result

Read the actual guide as a request author. Can its advice change a concrete
prompt decision for this model, and do the examples demonstrate that decision?
Check citations, variant qualifications, links to operation advice, and which
statements are recommendations. Passing repository tests or finding a route
does not prove the guide is useful.

If specialized prompting material remains unavailable after the search above,
save the known route and retain only useful supported technical advice and
clearly labeled agent judgment. Report where the search was limited; do not
claim an inaccessible page proves no guide exists or pad the file with generic
boilerplate. Missing guidance never makes the model unavailable.

## Keep execution ownership unchanged

Inspect the selected route's schema through `generation schema show` when request
preparation needs it, respecting Media Producer's current technical cache. Do not
create a model-specific schema, capability matrix, transport audit, or executable
adapter. Do not fetch alternative schemas just to fill discovery choices.

During preparation, explain a concrete input mismatch from the selected schema
or documentation, such as an image reference requested for a text-only endpoint.
Investigate an actual output/protocol failure when encountered; there is no
mandatory compatibility certification before adding or using a route.

Personal Markdown may add prompting practices, native notation, source links,
and user preferences. Keep it understandable without depending on old installation
paths. Review existing prose before refreshing and preserve deliberate preferences.
Do not interpret personal origin alone as authority over newer bundled curation.
